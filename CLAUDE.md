# Split the Bill: Master Constitution

This project follows the Solo Builder Model: one person + AI agents covering every SDLC role.

**What this is:** a responsive web app (like ขุนทอง from KBANK) for splitting restaurant bills. Organizer signs in with Google, creates a bill (menu items, prices, discounts, service charge, VAT), shares a link in the team chat (Slack); peers open the link with no login — on phone or desktop — tick their own items, and pay back via a generated PromptPay QR. The app tracks paid status per bill and a cross-bill "who still owes me" rollup.

## 🏗️ Core Architecture (Non-Negotiable)

- **Modification Constraint:** Always remember NOT to modify things not asked for. If not sure, ask.
- **All bill math lives in `src/lib/billing/` as pure functions** (discount application, service charge, VAT, per-person split, checksum, unpaid rollup). No money arithmetic in components, API routes, or the DB. This is the layer that must never silently break.
- **Money is integer minor-units everywhere, never a float.** THB satang is the only currency that ever settles a debt (store, compute, transfer, convert to ฿ decimal only at the display edge). A Bill's optional Purchase Currency amounts (see `CONTEXT.md`) are integer minor-units too, converted to THB satang exactly once via the Bill's FX Rate.
- **Two access modes, one rule:** organizer data is protected by Supabase RLS on `auth.uid()`; peers get capability-URL access only (unguessable bill ID, no accounts). Nothing peer-facing may require login.
- **Supabase is the single source of truth for bill state.** Clients read/subscribe (Realtime) and mutate through defined mutations; no duplicated client-side shadow state.
- **Responsive UI, mobile and desktop both first-class.** Every screen must work one-handed on a phone AND comfortably on desktop (peers open links from Slack on either); neither is "the enhancement".

## 🧪 Workflow: TDD Mandate

- **`src/lib/billing/`:** every new feature or logic change MUST use TDD (failing test → implement → verify green). The example CSV (`split-the-bill-example.csv`) is a canonical fixture: the Katsu bill must always compute Person A=179.10, Person B=187.20, Person C=179.10, Person D=143.10, Person E=214.20, checksum 902.70.
- **Components/UI:** post-implementation testing is acceptable.

## 🎨 Frontend & Design Standards

- Tailwind CSS; design tokens in `tailwind.config.ts` / `src/app/globals.css` are the source of truth.
- No em dashes in UI copy or chat replies.
- Minimum 12px font, accessible contrast, consistent spacing.
- UI copy is Thai-friendly: peer-facing screens must render Thai names/menus correctly and amounts as `฿1,234.50`.

## 🤖 Agent Team (Solo Builder Model)

Recap/triage/scope/plan run directly in the main session (see `solo-builder-kit`'s `loop/recap`, `loop/plan`). Subagents exist only where isolation (fresh eyes, parallelizable, run-unsupervised) is worth the cold-context cost:

| Agent | Step | Output |
|---|---|---|
| **`@split-the-bill-dev`** | Code | Feature code + tests + `STATUS.md` update |
| **`@split-the-bill-reviewer`** | Verify | Diff-scoped review findings, reported directly |
| **`@split-the-bill-qa`** | Smoke test | Browser test results (Playwright MCP), reported in chat |

## 🛠️ Definition of Done (DoD)

1. `npm run check` (lint + typecheck + unit tests) passes with ZERO errors. This is the identical command CI runs. (Wired up in the scaffold task; until then, DoD = the three underlying commands individually.)
2. Logic in `src/lib/billing/` has test coverage, including the canonical CSV fixture.
3. Peer-facing flows verified on a mobile viewport, not just desktop.

## 🤖 Git & Workflow

- **Commit Messages:** Conventional Commits (`type(scope): subject`), subject under 50 chars.
- **Approval policy:** pre-approved auto-commit + PR flow once a plan is agreed; ad-hoc/unclear-scope work asks for a green light first. Destructive operations (force-push, reset --hard, branch deletion, skipping hooks) always require explicit confirmation, regardless of the above.
- **Default branch:** `main`
- **Branch strategy:** semi-linear — feature branches rebase onto `main`, then `--no-ff` merge; never squash, never merge `main` into a feature branch.
