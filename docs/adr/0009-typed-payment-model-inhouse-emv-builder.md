# Typed payment fields, and an in-house EMV payload builder

Payment info is stored as **typed columns** on both `profiles` and `bills` — `promptpay_id`, `bank_name`, `bank_account`, `account_name` — replacing the earlier free-form `payment_info` + `payment_method` pair. The PromptPay QR payload is built by an **own pure function** in `src/lib/billing/`, not a runtime library.

Why typed and not the free-form pair: generating a QR requires knowing *for certain* that an identifier is a PromptPay ID, but a 10-digit string is ambiguous (a phone **or** a bank account). The old free-form model forced fragile label-parsing (`"promptpay"` vs `"KBank"` vs `"กสิกร"`, with typos) to decide whether to build a QR. A dedicated `promptpay_id` field removes the ambiguity; `bank_*` is the copyable fallback (spec's "PromptPay ID **and/or** bank-account text"). `account_name` is stored and shown next to the payback controls so the payer can confirm the recipient. All four appear as optional fields (profile "option 3") and degrade gracefully: PromptPay only → QR; bank only → copyable text; both → QR **+** bank fallback. The bill copies profile values as a **snapshot** at publish (a "follow profile" checkbox, default on), matching the existing copy-onto-bill model and honoring per-bill overrides (#5 US13).

Why own builder rather than the `promptpay-qr` library: the EMVCo/PromptPay payload is a **frozen public standard**, so a dependency's usual benefit — tracking upstream drift — is ~zero here, while it would place a black box in the money path against the "all money math pure, in `src/lib/billing/`, TDD" mandate (CLAUDE.md). The builder is ~40 lines (TLV fields + CRC16-CCITT); the satang→`"179.10"` formatting reuses `money.ts`. Correctness is anchored by **golden vectors captured once from `promptpay-qr`** in the tests, plus a real bank-app scan in QA — the library's proven output without a runtime dependency. QR *rasterization* still uses the `qrcode` library (Reed-Solomon layout is a solved, gnarly problem never worth hand-rolling).

Why migrate the legacy columns rather than leave them: additive would strand two forever-blank columns. Since `get_bill` is rebuilt and both `PeerBill.tsx` and `BillEditor.tsx` are edited for the new fields anyway, dropping adds negligible surface. A carry-over preserves settled-bill display: promptpay-keyword **or** (empty method + 10-digit `0…` phone) with valid 10/13/15 length → `promptpay_id`; else `bank_account` (+ `bank_name`). Live-inspected data confirmed real PromptPay rows exist, including a blank-method one a naive keyword rule would have misfiled — hence the phone-shape branch.

**Considered options:** free-form method+ID pair (ambiguous, can't drive QR); single method toggle (no both-at-once fallback); wrap `promptpay-qr` in a billing adapter (lower first-draft-bug risk but a dep in the money path); additive migration keeping the legacy columns (permanent blank cruft).
