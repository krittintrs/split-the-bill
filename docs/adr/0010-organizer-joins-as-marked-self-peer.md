# The organizer joins their own bill as a marked self-peer

The organizer eats too. They join their own Bill as a **real `peers` row**, auto-created on bill creation and reused across every bill, marked by a nullable `peers.linked_user_id → auth.users(id)` set to their own user id. "This row is the organizer of this bill" is the joinable predicate `p.linked_user_id = b.organizer_id`, never a name comparison.

Why a peer row and not a parallel concept: every downstream path is already keyed on `peer_id` — `ticks` (PK `line_item_id, peer_id`), `bill_peers`, `paid_at`, the `set_tick` / `set_paid` anon RPCs, and `computeBill`'s `tickedBy`. There is no way to tick a cell without a peer row, so an "organizer share" modelled anywhere else would need a second tick table and a second code path through the engine. The workaround organizers were already using (add yourself as a peer named after yourself) was the correct mechanism; this makes it first-class. Arithmetically the self-peer is an ordinary peer, so `src/lib/billing/` is untouched and the canonical Katsu fixture still holds.

Why marked rather than an indistinguishable peer: three behaviors need to tell you apart, and ADR-0005 already rejected name strings as the way to do it ("Ben", "ben " and "เบน" would be three people). The Unpaid Rollup must not report that you owe yourself; the Peer view must not offer you a PromptPay QR paying your own ID; and any future derived "everyone paid" must not wait on a Paid Flag you can never usefully toggle. `linked_user_id` is the exact column ADR-0005 reserved for post-MVP peer accounts, and it carries the same meaning in both uses: *this Peer record is that auth user*. The organizer's self-peer is a pre-claimed Peer, so **#12's Account Claim inherits a column that already exists with a proven query pattern** — at the cost of #12's My Debts needing the same `is distinct from b.organizer_id` guard so an organizer's own bills never appear in their own debts.

Why auto-add with opt-out rather than opt-in: the organizer eats on nearly every bill, so opt-in optimizes the rare case. Forgetting is not silent (`compute.ts` collects `untickedItemIds` and unticked items contribute ฿0, so the Checksum falls short of the Receipt Total), but a bill you eat on and are absent from is still wrong-by-default. On the rare bill you only paid for, remove your own chip, or simply leave it unticked: a Peer owing ฿0 already gets no QR and no payback controls. `createBill` finds the self-peer by `linked_user_id` and inserts only when absent, so exactly one exists per organizer; a collision with `unique (organizer_id, name)` adopts the existing row rather than throwing, since bill creation must never fail on a name clash.

Why a new `profiles.display_name` rather than reusing `account_name`: the self-peer's name is **peer-facing** — it labels a matrix column on the shared link — so it cannot be "ฉัน", which every peer would read as themselves. `account_name` is the bank *account holder* name kept for payer confirmation (ADR-0009); it is formal, often long, and empty until payment info is entered. `display_name` defaults from the Google identity, is editable on the existing `/profile` page, and falls back to the Google name then the email local part so a matrix header is never blank.

Behavior on the shared link: the self-peer's ticks and Peer Total are **visible** (peers can see the organizer covered their own share, and the totals reconcile against the receipt), badged เจ้าของบิล, but the row is not tappable and shows no QR and no Paid Flag. Suppression is UI-only — `set_paid` still accepts the self-peer's id from an anon caller — which is harmless because no rollup reads that flag. In the Unpaid Rollup the organizer's share is **excluded from debt but shown as context** (คุณจ่าย / ส่วนคุณ / ค้างรับ), so the figures reconcile instead of silently omitting the organizer's share.

Existing data is left alone: no backfill onto past bills and no adoption of a hand-made workaround peer, which stays an ordinary Peer. The rollup surfaces only *unpaid* peers, so a settled past bill never exposes the stale row, and deleting it by hand is a one-row fix. Backfilling would instead rewrite already-shared bills. Note the deploy ordering is the **#26 shape, not the #10 shape**: this migration adds what the new code reads, so it must run *before* the Vercel deploy, and `isSelf` is typed optional so a deploy that wins the race degrades the row to an ordinary peer instead of throwing during SSR.

**Considered options:** organizer as an implicit column materialized only on first tick (no empty columns, but every view and the realtime refetch path must render a column with no peer id); plain peer plus an "add me" button (zero schema, but permanently indistinguishable — the rollup says you owe yourself and the peer link offers you a QR to pay yourself); name-matching to identify the organizer (the fragility ADR-0005 exists to prevent); a separate `is_self` boolean (a second column meaning what `linked_user_id` already encodes, and it would not serve #12); hiding the self-peer from the shared link (peers would see dishes ticked by nobody and totals that miss the receipt).
